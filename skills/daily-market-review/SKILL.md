# 每日市场复盘

整理、补充、修正和展示指定已收盘交易日的资本市场总体复盘数据。不做买卖建议。

## 适用场景

- 请整理今天的复盘数据
- 生成 2026-08-21 的总体复盘
- 补齐两融
- 从这张图片提取 2026-08-21 的复盘数据并保存
- 从这个链接读取今日两融数据并保存
- 600519 今天是四板
- 把上涨家数修正为 3210
- 以这张同花顺截图为准，修正市场宽度
- 查看已保存的历史总体复盘

## 架构

- 持久化与查询：`packages/marketreview`
- 交易日历与指数日 K：`packages/marketdata`
- 本 Skill 负责理解请求、取得数据、完成业务校验后写入；用户要求查看时读取、统计并展示

默认数据库：`<workspace>/stockpilot/db/market_review.sqlite3`

必须调用 `packages/marketreview` 的稳定入口读写，不经过独立 CLI，也不直接操作 SQLite。数据库不关心数据来自 API、网页、图片还是用户文字，只接收完成解析和校验后的最终字段或事件。图片、链接、采集方式和证据不入库。

## 操作分流

写入和显示是两个独立操作。只有用户要求整理、补充、提取或修正时才修改数据库。用户只要求查看时，只读库、统计并展示。

写入分两阶段，不要把整次请求一刀切：

1. **先确定请求范围**
   - 完整复盘：例如“整理今天的复盘”“从这张图片提取复盘数据”
   - 点名字段或类别：例如“补齐两融”“修正上涨家数”“读取今日两融”
2. **再仅对范围内字段分配来源**
   - 用户为该字段指定了图片、链接、网站或具体值 → 指定数据或来源
   - 范围内且未指定来源 → 自动整理
   - 范围外字段一律不取、不写

混合示例：

- “补齐两融”：范围只有两融字段，自动整理这些字段，不顺带整理整个复盘。
- “补齐三大指数”或“补齐上证指数”：范围只有对应指数字段，必须尝试通过 `marketdata` 自动获取这些指数，不顺带整理整个复盘。
- “从这张图片提取复盘数据”：范围是完整复盘；图片中能识别的受支持字段都可写入。
- “整理今天复盘，用这张图核对上涨家数”：范围是完整复盘；只有点名的上涨家数走该截图，截图里其他可识别字段不接管；其余范围内字段走自动整理。
- 指定来源时，除非用户同时要求把范围外或其他未点名数据也自动补齐，否则不要另找来源扩大范围。

## 未指定数据源：自动整理

例如：请整理今天的复盘数据；补齐两融。

1. 用 `packages/marketdata` 交易日历确定已收盘目标交易日。未指定日期时落到最近一个已收盘交易日。
2. 仅对请求范围内、且未指定来源的字段，主动使用可用数据源。
3. 解析、交叉检查、转换单位。
4. 只将成功取得且校验通过的数据写库。
5. 一次性列出范围内未取得的项目，用户可以跳过。
6. 不用前一日数据或猜测值补空缺。

这里的自动是 Agent 自主选择获取方式，不代表每个指标都有固定自动 API。

当前明确自动承诺的只有三只指数日 K：上证 `sh000001`、深证成指 `sz399001`、创业板指 `sz399006`。请求范围包含哪些指数字段且未指定来源，就必须尝试对应指数；取得后将当日收盘和前收盘作为普通原子字段写入；失败的指数不进入本次写入，不用其他日期顶替。范围不含指数时不要顺带取指数。

范围内的涨跌停、两融、市场宽度、成交额、市值、PE、平均股价属于尽力通过 API 或网页取得。网页失败时不能猜值。

## 指定数据或来源

例如：从这张图片提取并保存；从这个链接读取今日两融；600519 今天是四板；把上涨家数改成 3210。

只处理请求范围内、且用户指定的数据或来源。

- 图片 / 截图：在请求范围内，提取图中明确出现且能识别的字段和单位。看不清、截到一半、对不上字段名时不得入库。若用户只点名核对某字段，只写入该字段，即使图中还有其他可识别字段。修订截图时只更新允许写入的字段，不清空图里没有出现的字段。
- 链接 / 网站：提取指定日期、且落在请求范围内的数据。页面日期与复盘日期必须一致；失败时不能猜值。
- 用户文字：将自然语言转换成原子字段或涨跌停事件。
- 同一请求里两个指定来源对同一字段数值冲突：不写该字段，向用户说明。

### 不可独立入库的派生汇总值

有效涨停数、涨停炸板数、打开跌停数、收盘跌停数、首板数、连板数、最高板、最高板代表、炸板率、连板率、涨跌停比等是读取事件后统计的派生值，数据库没有对应原子字段。

- 可执行示例：`600519 今天是四板` → 写成该股有效涨停事件，并带 `streak_height=4`。
- 若图片或文字只给出“最高板是四板”“有效涨停 52”等汇总值，而没有个股事件明细：不得把汇总值当成字段写入；应提示需要个股触板事件（代码、方向、收盘状态、涨跌幅限制、连板高度）。

## 入库闸门

所有写入都走同一流程：

```text
确定请求范围
        ↓
图片 / 链接 / API / 用户文字（仅范围内）
        ↓
提取候选数据
        ↓
确认交易日期、字段含义和单位
        ↓
执行市场规则和输入类型校验
        ↓
转换成复盘原子字段或涨跌停事件
        ↓
调用 packages/marketreview 写入
```

看不清、日期不一致、单位不明确、无法完成业务校验、或多来源对同一字段冲突时，该字段不入库，并向用户说明。不要猜测单位，不要用其他日期顶替。

落库前：

1. 确认目标日是已收盘交易日。用户显式指定非交易日：不落库，并提示最近交易日。目标日为当日且尚未收盘：拒绝正式记录。暂以 A 股 15:00 为日度收盘边界。
2. 在 Skill 层检查市场、代码、方向、收盘状态、涨跌幅限制、证券宇宙、ST 排除和输入类型；口径见 PRD 第 9、10 节。
3. 通过后打开 `MarketReviewRepository(default_market_review_db_path())` 写入。

repository 和 SQLite 不重复业务校验，不判断事件是否真实，也不自行计算或复核 `streak_height`。来源只用于本次判断，不进入当前数据库。用户查看后认为数据有误时，可要求修订或覆盖。

## 修订语义

原子字段：未提到的保持原值；具体值更新，包括 `0`；显式“清空”写入 `null`。

涨跌停事件：同一「日期 + 市场 + 代码 + 方向」覆盖原事件。空列表保存是 no-op，不代表清空；清空某日或某条事件使用删除接口。

方向属于唯一键。如果原来保存为涨停、实际是跌停，必须调用 `replace_price_limit_event_direction(...)` 在同一事务中删除旧方向并写入新事件。不要分开调用 `delete_price_limit_event` 再 `save_price_limit_events`，否则新增失败时会永久丢失旧事件。

每条事件都写入 `streak_height`：用户给了连板数就采用用户值；用户没给时，有效涨停根据日历前一交易日同股已保存事件计算，前日有效涨停则高度加一，否则写 `1`；炸板和跌停写 `0`。

YAML 示例见 PRD `docs/marketreview/daily_market_review_skill_prd.md` 第 5.2 节。

## 显示

1. 用 repository 读取总体复盘原子字段和涨跌停事件。
2. 根据当前已保存数据统计有效涨停、涨停炸板、打开跌停、收盘跌停、首板、连板和其他展示指标，再按 PRD 八类表格格式化。原子字段为 `null` 时留空；总体复盘或涨跌停事件任一存在，就展示当日组合视图；两者都不存在时才显示无数据。
3. 显示时不自动取数、不追问缺失数据、不判断完整性、不修改数据库。

Skill 自行完成统计和单位换算：元→亿元/万亿元，小数比率→百分数。package 返回原始原子值和每日涨跌停事件。

## 边界

- 写入和显示相互独立；只有用户要求写入时才修改数据库
- `packages/marketreview` 不提供指数采集编排接口
- 有效涨停、涨停炸板、打开跌停、收盘跌停、首板和连板均由 Skill 根据当前已有事件统计，不保存重复聚合值
- Skill 负责写入前的业务校验；repository 不重复验证数据内容是否符合真实市场
- 来源、网页链接、图片和采集方式不入库
